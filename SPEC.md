# SPEC.md — Article Brief

## 1. Purpose

Article Brief is a personal, single-screen web tool: paste the text of a press article, get back a summary of its main ideas, generated by a local LLM. It exists to make full-length article summarization as effortless as the newsletter triage already handled by Newsletter Digest, without the overhead of accounts, history, or a backend — the tool is stateless by design.

## 2. User flow

1. User opens the app — locally on the Mac Mini, or remotely from any device over the existing Tailscale network. The app loads in the **idle state**: empty text area, placeholder "Collez l'article.", "Résumer" button visible but disabled, no language indicator (nothing to detect yet).
2. User pastes the full text of an article into the text area. This moves the app to the **filled/ready state**: a word count appears near the button, and "Résumer" becomes enabled. Next to the word count is either a plain "modèle local" label (remote target not configured, see §5) or **a local/remote switch** (`src/components/ModelSwitch.tsx`, `desktop/mobile-05-filled-remote.png`): a single button showing the currently selected target's name plus a swap glyph ("⇄") — clicking it toggles between "modèle local" and "modèle distant". The switch is disabled during generation and always defaults to local on page load (no persistence, §2.12). No other layout change.
3. User clicks "Résumer." Generation starts immediately in place — there is no intermediate loading screen before the first token arrives.
4. The app detects the article's language client-side (French or English — see §3). The result is available before generation completes and is shown as a small indicator ("FR détecté" / "EN détecté") as soon as it's ready.
5. The app sends the full article text to Ollama's streaming generate endpoint, using the prompt matching the detected language (see §4).
6. The summary streams into the result area token by token: the introductory sentence composes progressively with a blinking cursor at the end of the in-progress text, then the bullet points (3–10 items, per `computeTargetPoints`, §4) appear one by one once the intro is complete. There is no generic "generating…" placeholder — the streaming text itself is the progress indicator.
7. During generation, the branding/idle header is replaced by a back-to-source control ("↩ Source" + word count, plus "· modèle distant" when the remote target is active — nothing extra for local, `desktop/mobile-08-streaming-remote.png`), shown but disabled — the user cannot interrupt a generation in progress.
8. Once generation completes, the back-to-source control becomes enabled (clicking it returns to the text area with the original pasted text, e.g. to edit and resubmit), and a "Copier le résumé" button appears below the bullet list.
9. Clicking "Copier le résumé" copies the summary to the clipboard and shows a transient "Copié ✓" confirmation for ~1.6 seconds, then reverts to the initial label.
10. User can toggle light/dark mode manually at any time via a persistent control in the header; the toggle applies for the current page load only (no storage of the preference — consistent with §2.12).
11. **Error path** (`src/components/ErrorNotice.tsx`; `desktop/mobile-06-error-unreachable.png`, `desktop/mobile-07-error-empty.png`; extended in session 6 for the remote target). Three failure modes share one rule set:
    - **Target unreachable** — Ollama doesn't respond when "Résumer" is clicked, or the stream is interrupted mid-generation (both collapse to the same handling: a thrown/rejected `streamSummary` call, `src/lib/ollama.ts`).
    - **Stream completes but the final response is empty after trim** — the entire generation budget was consumed by a "thinking" model's hidden reasoning (§4/§9), a distinct case from the one above.

    In every case, an inline block appears between the text area and the button (not after everything): a small "Échec" heading, an italic, target-aware message, and a muted hint line. The view stays on the source layout, so no back-to-source step is needed — the branding/idle header is unchanged.

    | target | kind        | message                                         | hint                                                                                   |
    | ------ | ----------- | ----------------------------------------------- | -------------------------------------------------------------------------------------- |
    | local  | unreachable | `Impossible de joindre le modèle local.`        | `Vérifiez qu'Ollama tourne sur le Mac Mini` [`, ou basculez sur le modèle distant`]`.` |
    | local  | empty       | `Le modèle local n'a pas produit de réponse.`   | `Relancez` [`, ou basculez sur le modèle distant`]`.`                                  |
    | remote | unreachable | `Impossible de joindre le modèle distant.`      | `Vérifiez la connexion` [`, ou basculez sur le modèle local`]`.`                       |
    | remote | empty       | `Le modèle distant n'a pas produit de réponse.` | `Relancez` [`, ou basculez sur le modèle local`]`.`                                    |

    (the bracketed switch clause only appears when the other target is actually available — local is always available, so the remote rows always carry it; always ends with a period either way.)

    "Résumer" is immediately relabeled **"Réessayer"** and stays clickable — clicking it retries with the current text and current target. No automatic retry, ever. Any change of target, or any edit to the text, clears the error and resets the label back to "Résumer" — permanently, until the next error: switching back to the target that just failed does **not** restore "Réessayer" (nothing remembers which target failed). The pasted text is always preserved.

12. Nothing is saved anywhere. Refreshing or closing the tab clears everything and returns to the idle state — this is expected behavior, not a bug, including if it happens mid-stream (no partial-state recovery).
13. Pasted text may carry site boilerplate ahead of the real article — sharing instructions, legal notices, a syndication contact, paywall messaging, a bare URL on its own line. Only a standalone URL line (the entire line is nothing but a URL) is stripped client-side (`src/lib/text-cleanup.ts`), and only from the copy of the text used for language detection and the Ollama prompt — never from the text area's own state, the back-to-source content (§2.8), or the word count (§2.2). Everything else — legal notices, sharing instructions, syndication contact lines — is left for the model to recognize and ignore per the prompt instructions (§4). This is a deliberate scope boundary, not a gap to close later.

## 3. Language detection

- Ported from Newsletter Digest's validated approach, no external library, then refined for Article Brief: full articles are longer and more likely to contain a quoted sentence or aside in the other language than Newsletter Digest's short newsletters, which exposed a gap in the original single-list threshold (see below).
- Count French-language markers against the exact 24-word list from Newsletter Digest's source (`_FRENCH_MARKERS`): `le`, `la`, `les`, `de`, `du`, `des`, `en`, `un`, `une`, `est`, `sont`, `qui`, `que`, `dans`, `sur`, `par`, `pour`, `avec`, `mais`, `ou`, `et`, `donc`, `car`, `si` — as a percentage of total word count in the pasted text.
- Count English-language markers the same way, against a matching 24-word list, structurally comparable to `_FRENCH_MARKERS` by category (articles, common prepositions, conjunctions, forms of "to be", relative pronouns) and disjoint from it: `the`, `a`, `of`, `in`, `on`, `at`, `by`, `for`, `with`, `from`, `to`, `but`, `or`, `and`, `so`, `because`, `if`, `is`, `are`, `was`, `were`, `who`, `that`, `which`.
- Detected language is whichever list has the higher density (% of total words) — a proportional comparison, not a single fixed threshold. Ties (including text with no markers from either list) default to English.
- Rationale for the proportional comparison over the original single-list 8% threshold: French sentences naturally pack far more marker-list words per sentence than English does (articles, contractions, prepositions are more frequent), so a single short French sentence embedded in an otherwise English article could cross 8% of the _total_ word count even with English as the clear majority — particularly once paragraph breaks are lost, e.g. from a web-page copy/paste collapsing the text into one block. Comparing densities in both directions is robust to this.
- Detection runs client-side, once, on the full pasted text, before sending anything to Ollama — the result determines which prompt is used (§4) and is then displayed as the language indicator once generation starts (§2.4). Do not re-run detection on partial/streamed output.
- Confirmed: detection stays entirely client-side (the stopword function above). The "détecté" language indicator in the mockups simply reflects this client-side result once it's available — there is no LLM-side detection step.

## 4. Prompts

- Two separate, hardcoded prompts — French and English — never a single bilingual prompt (see CLAUDE.md decision #4 for why).
- **Correction**: the anglicism fix on Newsletter Digest is the French prompt written entirely in French — no English framing or instructions mixed in — not few-shot examples. Newsletter Digest's actual source code confirms this; an earlier version of this spec (and of the blog post describing the project) attributed the fix to few-shot examples, which was inaccurate. Do not add few-shot examples to the French prompt on the assumption they're the validated technique.
- Both prompts instruct the model to output: one short, original introductory sentence stating what the article is about (never reusing the headline verbatim), followed by a blank line, then approximately `computeTargetPoints(wordCount)` bullet points capturing the article's main ideas, each bullet starting with an em dash ("—") at the start of its line.
- **Second correction — intro too close to the article's opening wording**: the headline-verbatim guard above only fires when a headline is present in the pasted text; once boilerplate is stripped, the common case has no headline at all (see the boilerplate root-cause note below), which left the model free to closely rearrange the article's own opening sentence instead of writing an independent one. Confirmed on a live repro (Le Monde, Evergrande article): the generated intro was a near word-for-word rearrangement of the article's actual opening sentence. Both prompts now add, in both sandwich locations, alongside the existing headline-verbatim clause (an addition, not a replacement) — French: "Ne pas se contenter de réorganiser les mots de la première phrase de l'article : formuler cette introduction avec un vocabulaire et une construction différents de ceux du texte source."; English: "Do not merely rearrange the wording of the article's opening sentence: phrase this introduction using different vocabulary and sentence structure than the source text."
- **Coverage and grouping are qualitative instructions; the numeric target is a soft continuation anchor that measurably improves — without guaranteeing — full-article coverage**: the prompt asks the model to cover the article from start to finish (not just its opening sections) and to group related ideas under a single point rather than listing them separately, alongside an "about N points" figure from `computeTargetPoints` (≈1 point per 300 words, clamped 3–10, `src/lib/prompts.ts`). The model does not follow this number literally — a real ~2900-word article produced 18 points against a "~10" target. Across this session's manual testing on that same article: **with** the target in the prompt, three comparable runs gave `eval_count` 1014 (full coverage to the article's conclusion), 1086 (full coverage), and 841 (stopped roughly three-quarters through, before the article's final section); the one comparable run **without** the target gave `eval_count` 921 and stopped around two-thirds through, with points trending more verbose/paraphrase-heavy. None of these runs were truncated by `num_predict` — all stopped well under the ~1450–1600 budget for this article length, confirming this is the model's own stopping judgment, not a technical limit. This is accepted, documented behavior for a local 7B model at `temperature: 0.2` (an existing, deliberate decision — not revisited here): some run-to-run variance in exactly when the model decides a summary is "complete" is inherent to a local 7B model and not fully eliminable through prompt wording alone. It is not something the client attempts to detect or compensate for (e.g. no retry-on-short-output logic). If it proves too inconsistent in regular use, revisit as a fresh discussion rather than assuming more prompt wording changes are the answer — a lower temperature or a different model are the next things to weigh, not further prompt tuning.
- **Numeric target, coverage, grouping, and format are all sandwiched, not stated once**: the target point count, the coverage instruction, the grouping instruction, and the intro/blank-line/em-dash format instructions all appear in the main instruction paragraph before the article text, and are repeated together in a reminder immediately after it. On the real ~2900-word article, instructions positioned only before the article text lost influence by the time generation reached the end on the 7B model — first producing far more points than an earlier fixed cap allowed, then, once the cap alone was sandwiched, losing the intro/blank-line/em-dash structure entirely because the cap-only reminder became the dominant instruction by recency. The full set of target + coverage + grouping + format instructions is repeated after the article text to stay close to the generation point.
- **Boilerplate-awareness instruction, also sandwiched**: both prompts instruct the model to expect that the provided text may be preceded by sharing instructions, legal notices, or a standalone URL (§2.13) before the article actually starts, and to locate the real start rather than treat that boilerplate as content — repeated in the post-article reminder alongside an explicit "never a separate title or heading line" instruction. Root cause on the real repro (a Le Monde article) wasn't the model echoing the actual headline — the headline never appeared in the pasted text — but a paraphrase of the article's opening sentence, produced after the model worked through sharing/legal/URL boilerplate that preceded the real content.
- **Streaming output contract**: the client parses the raw token stream on this same structure — text before the first blank line is the intro sentence; each subsequent line starting with "—" is a new bullet. No structured format (e.g. JSON) is imposed on the model — a small local model is more likely to break a strict format mid-stream than to drop the blank-line/dash convention, and the convention is trivial to parse incrementally.
- Ollama generation parameters:
  - `temperature: 0.2`
  - no `stop` token (removing it fixed premature truncation on Newsletter Digest)
  - `num_ctx: 8192`
  - `num_predict`: scaled directly from article word count via `computeNumPredict(wordCount) = Math.round(wordCount * 0.65) + 350` (`src/lib/prompts.ts`), clamped between 500 and 2200 — deliberately independent of `computeTargetPoints` above, not chained through it. An earlier version keyed `num_predict` off the target point count; that coupling was dropped because the target didn't reliably predict actual output length, producing a too-tight budget (an observed `eval_count` of 1014 against a computed cap of 1050 on the ~2900-word test article). Revised during session 4 wrap-up: a second real article (~2150 words) hit a hard mid-sentence truncation at `eval_count` 1113 against the original formula's computed cap of 1118, despite that formula having given comfortable headroom (cap 1455 vs. observed `eval_count` up to 1086) on the ~2900-word article it was derived from — output verbosity doesn't track word count closely enough for a tight fit. Since `num_ctx` (8192) leaves ample room relative to `prompt_eval_count` values seen so far, and a higher `num_predict` costs nothing on runs that stop naturally before reaching it, the fix widens the margin rather than re-fitting the curve from two noisy data points. Still not a calibrated formula — see open item in §9.
- **Per-target generation parameters** (`src/lib/model-profiles.ts`, session 6): the parameters above are the **local** target's (`llama3.1:8b`) — local has no overrides, so `buildGenerationParams(LOCAL_PROFILE, numPredict)` reduces to exactly them. The **remote** target (`gpt-oss:20b`) adds two profile-level overrides:
  - `reasoningAllowance: 1500`, added on top of `computeNumPredict`'s own budget. `gpt-oss:20b` is a "thinking" model whose hidden reasoning is streamed as a separate `thinking` field alongside `response` (see below) — but `num_predict` caps **both combined**, not response alone. Confirmed live, not assumed: a 6-call experiment against the real remote host at a deliberately tight `num_predict: 80` was consumed entirely by reasoning in every single case (0 response tokens, `done_reason: "length"`), reproducing the diagnostic session's empty-output failure on demand. A second, larger experiment (the real French prompt, a ~1660-word synthetic article, `num_predict: 4000`) measured the actual overhead beyond `computeNumPredict`'s own allocation across four runs: 1121 / 664 / 638 / −194 tokens. `reasoningAllowance: 1500` gives margin above the worst of those — the same "widen the margin, don't tight-fit a few noisy points" approach already used for `computeNumPredict` itself. Still a first cut — see §9.
  - `numCtx: 10240`, raised from the shared default of 8192. Extrapolating the same experiment's `prompt_eval_count` (2783 tokens for the 1661-word article) to a ~2900-word article (this doc's existing reference article length) gives roughly 4514–4859 prompt tokens depending on projection method; adding the worst-case remote `num_predict` (`computeNumPredict`'s clamp ceiling of 2200 + the 1500 `reasoningAllowance` = 3700) totals 8214–8559 — both **exceed** 8192. Trade-off, accepted deliberately: a per-request `num_ctx` that differs from whatever the shared remote host currently has loaded forces a model reload there (a real, bounded, visible latency cost) — but staying at 8192 risks silent context overflow (truncation or a context-shift eviction, with no error surfaced to the app at all), which is worse than a bounded, visible cost.
  - `think` is deliberately **not set** for the remote profile. The same two live experiments tested every value Ollama accepts (unset, `true`, `false`, `"low"`, `"medium"`, `"high"`): at a tight budget all six behaved identically; at a generous budget the three effort levels showed no reliable relationship to total token cost — the two `"low"` runs in the second experiment were the highest _and_ lowest of the whole set, a ~1300-token swing at the same level on the same article. `think: false` also did **not** suppress reasoning on the remote host's Ollama version (0.32.13), contradicting what the model's own `/api/show` chat template implied it would do. None of this is a dependable lever, so the remote profile omits `think` entirely and relies on the budget/hint/error-contract mitigations above instead.
- **Hidden reasoning is never surfaced.** A "thinking" model's `thinking` field (Ollama's NDJSON output streams it separately from `response`) is filtered out inside `streamSummary` (`src/lib/ollama.ts`) before a single character reaches the UI — never displayed, never copied, never counted toward the visible output. Confirmed live: a real remote generation logged `reasoning_chars: 2438` in the console while the on-screen summary contained none of it. The done-chunk console log (already logging `prompt_eval_count`/`eval_count`) now also logs `done_reason` and this `reasoning_chars` count, to support future recalibration of the values above.

## 5. Ollama configuration

- **Local target** — machine-level, not application code:
  - `OLLAMA_HOST` must be set so Ollama listens beyond `localhost`, allowing browser requests over the Tailscale network.
  - `OLLAMA_ORIGINS` must include the app's origin so the browser's CORS preflight succeeds.
  - These are one-time configuration steps on the Mac Mini, not something the application code manages.
  - **Base URL, resolved at runtime**: the frontend calls `http://${window.location.hostname}:11434`, never a hardcoded hostname or a build-time environment variable. This works unchanged whether the page was loaded via `localhost` (local use) or a Tailscale hostname (remote use), and needs no reconfiguration if the Tailscale name ever changes.
- **Remote target** (`gpt-oss:20b`, session 6) — a trusted, privately administered server reachable over Tailscale, CLAUDE.md decision #1's narrow exception:
  - Base URL comes from `VITE_REMOTE_OLLAMA_HOST` in `.env.local` — a build-time env var, gitignored (the repo is public, the real address must never be committed; `.env.example` documents the expected shape: a full `scheme://host:port`, not a bare hostname). If unset, the remote target is simply unavailable — the app falls back to the plain "modèle local" label with no switch shown (§2).
  - The remote host's `OLLAMA_ORIGINS` currently allows only `http://localhost:5174` — not a Tailscale hostname, not `127.0.0.1`, not a phone over Tailscale. Widening that allowlist is a known prerequisite for a future session, not addressed here.
- **`num_ctx` is sent per request, not machine-level configuration** — correcting an earlier version of this document, which claimed otherwise. `buildGenerationParams(profile, numPredict)` (`src/lib/prompts.ts`) sets `num_ctx` on every generation call: `8192` by default, `10240` for the remote profile specifically (derivation in §4). The Ollama-side configuration in this section (`OLLAMA_HOST`/`OLLAMA_ORIGINS`) is the only genuinely one-time, machine-level piece left.
- **Vite dev/preview server**: listens on `0.0.0.0` (not `localhost` only) so it's reachable over Tailscale, and is pinned to port `5174` with `strictPort: true` (session 6) — the remote host's `OLLAMA_ORIGINS` allowlist above depends on the exact origin including the port, so a silent fallback to a different port would break the remote target's CORS invisibly.

## 6. UI / Design

- Single screen, no routing, no sidebar, no history list. "Back to source" (§2.7–8) is a local state toggle within the same screen, not a navigation change.
- States to implement, each validated in `/design`: idle, filled/ready, streaming, done — for both desktop and mobile breakpoints (8 mockups), plus, added in session 6, filled/streaming with the remote target active and both error states, also for both breakpoints (8 more mockups, 16 total — see CLAUDE.md reference section for filenames).
- Elements across states: paste text area, "Résumer"/"Réessayer" button (disabled when empty), word count + either a plain "modèle local" label or the local/remote switch (§2), language indicator, streaming result area (intro sentence + bullet list), back-to-source control (+ target segment when remote is active, §2.7), "Copier le résumé" button (conditionally shown, with transient "Copié ✓" state), manual light/dark toggle.
- Error state (`desktop/mobile-06/07`, §2.11): the "Échec" block sits between the text area and the button, not after everything; "Résumer" relabels to "Réessayer" and stays clickable, pasted text untouched. Styled consistently with the rest of the screen (same typography/colors), not a separately invented visual treatment.
- Design tokens (from the validated mockups — useful as exact reference values; `/design` remains authoritative for layout, spacing, and copy):
  - Colors: paper background `#f3f2f2`, ink `#201e1d`, accent terracotta `#c1440e` (light mode) / `#ff9d52` (dark mode) — replaces a default system cyan — magenta `#d6006c` for the bullet-point dashes.
  - Typography: Source Serif 4 throughout, including buttons — no sans-serif anywhere.
  - Layout: a single breakpoint around ~600px switching between a wider and a single-column layout; everything else fluid (`clamp()` on font sizes and spacing) rather than discrete breakpoints.

## 7. Non-functional requirements

- No accounts, no persistence. Data leaves the local machine only when the user explicitly selects the remote target (§2) — and even then, only to a single trusted, privately administered host on the private Tailscale network, never to a public API or third-party service (session 6).
- Usable on both desktop and mobile viewports (accessed remotely via Tailscale while traveling).
- Zero ongoing cost — no paid API; models run locally or on a privately hosted server.

## 8. Testing scenarios

- Very short pasted text (edge case for the 8%-stopword language detection threshold).
- Long article approaching or exceeding the 8192-token context window.
- Article with substantial mixed French/English content.
- Ollama unreachable (e.g., Mac Mini asleep or not running Ollama) — shows the §2.11 inline error and re-enables "Résumer," never a silent hang.
- Streaming response interrupted mid-generation (network drop over Tailscale) — same error path as above, not a partial/frozen summary.
- Reload mid-stream — must return cleanly to the idle state, no partial-state recovery attempted.
- Malformed model output missing the expected blank-line/dash structure (§4) — the parser should degrade gracefully (e.g. treat everything as the intro) rather than throw.
- "Résumer" stays disabled on an empty/whitespace-only text area.
- Back-to-source control is inert (non-interactive) during generation and becomes interactive only once generation completes.
- "Copier le résumé" only appears after generation completes; the "Copié ✓" confirmation reverts to the default label after ~1.6 seconds.
- **Session 6 (remote target / extended error contract):**
  - Remote target unreachable (bad host/port, or the remote machine down) — shows the §2.11 error with the target-aware "modèle distant" message and hint, same immediate re-enable ("Réessayer") as local.
  - Stream completes but the final response is empty after trim (a thinking model consumed its entire budget on hidden reasoning, §4/§9) — shows the distinct "n'a pas produit de réponse" message, not the unreachable one.
  - Switching target, or editing the pasted text, while an error is showing — clears the error and resets the button label to "Résumer"; switching back to the target that just failed does not restore "Réessayer".
  - Local/remote switch is disabled during generation and always defaults to local on page load.
  - Header shows the active target ("· modèle distant") during remote streaming and once done; no target segment when local is active.
  - No env var configured — plain "modèle local" label, no switch, identical to pre-session-6 behavior.

## 9. Open items / assumptions to validate

- Exact `computeNumPredict` formula: revised during session 4 wrap-up after a real hard truncation — `computeNumPredict(wordCount) = Math.round(wordCount * 0.65) + 350`, clamped 500–2200. Replaces the first word-count-based version (`0.45×words + 150`, clamped 500–1600, itself replacing an earlier numeric-point-target-based version and, before that, a fixed `num_predict: 600`). That first version was derived from a single ~2900-word article (`eval_count` 1014, comfortable headroom against its 1455 cap) but didn't generalize: a ~2150-word article produced a more verbose set of points and hit a hard mid-sentence cutoff at `eval_count` 1113 against a computed cap of 1118. The revision is a deliberate margin increase, not a tighter curve fit, made safe by the fact that `num_ctx` (8192) leaves ample headroom relative to `prompt_eval_count` values observed so far and that a higher `num_predict` doesn't cost anything on runs that stop naturally before reaching it. Still based on only two real articles, so still not a calibrated formula. `prompt_eval_count`/`eval_count` continue to be logged to the console on each generation (see §4) to gather real token-count data; re-tune from that data against a wider range of article lengths once enough accumulates.
- Whether to expose `repeat_penalty` as an explicit generation parameter: currently left at Ollama's default (no explicit value set) for both profiles. Worth considering if repetition persists after the `num_predict` tightening and prompt sandwiching land, but not added yet — needs its own real-article test pass first; would apply per-profile alongside the other `GenerationOverrides` (session 6, §4) if it's ever added, unrelated to session 6 otherwise.
  - First concrete field signal: during session 4 validation (manual test on a French article, outside the dedicated test protocol), a summary produced two consecutive near-identical points, one an exact word-for-word duplicate. A single observed instance, with no `eval_count` or generation parameters captured at the time — not enough on its own to decide on `repeat_penalty`, but worth cross-referencing against further occurrences before reopening this point.
- Behavior when Ollama is unreachable because the Mac Mini is asleep: Newsletter Digest relies on Wake-on-LAN for this scenario. Whether Article Brief should trigger the same WoL mechanism, or simply surface a clear "unreachable" error and let the user wake the machine themselves, is not yet decided.
- **Remote profile's `reasoningAllowance` (1500) and `numCtx` (10240) are a first cut, not calibrated** (session 6, §4): derived from two live experiments against the real remote host — a 6-call mechanism check at a deliberately tight budget, and a 4-call calibration run on a single ~1660-word article. Those four calibration runs alone swung by ~1300 tokens between two runs at the _same_ `think` level, so this rests on very little data. The extended console logging (`reasoning_chars`, `done_reason`, alongside the existing `prompt_eval_count`/`eval_count`) exists specifically to gather more real-usage data for future recalibration — the remote profile now shares `computeNumPredict`'s existing "log and revisit, don't over-fit a few data points" posture above.
- **A non-empty response with `done_reason: "length"` is a silently truncated summary.** Accepted and logged only, consistent with the existing no-client-side-compensation stance (§4: no retry-on-short-output logic) — but expected to be _more_ frequent on the remote profile than local, precisely because a "thinking" model's reasoning eats unpredictably into the same shared budget. Not detected or surfaced any differently from a normal completion; watch the console log if a remote summary seems unexpectedly short.
